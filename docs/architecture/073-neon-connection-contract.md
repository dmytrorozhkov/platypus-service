## Required behavior

1. Add an opt-in importable adapter, with no new executable/server/Lambda wiring. Use already pinned pg8.23.1; no dependency installation or migration setup.
2. Define readNeonConfiguration(environment) with explicit separate NEON_HOST, NEON_DATABASE, NEON_USER, NEON_PASSWORD. No guessing values from OS, PG*, DATABASE_URL or local defaults. Reject URL syntax, IPs, loopback, suffix spoofing, control characters and malformed identifiers/hosts before pool construction. Require an AWS Neon pooled endpoint; do not tie preparation to an accepted new region or create an endpoint. Use fieldwise config rather than a connection string. Errors never echo supplied fields/passwords/URLs. Runtime database identity must be explicit; no admin-role assumption.
3. Verified TLS with rejectUnauthorized:true and hostname verification; never permit env/URL TLS downgrades or custom insecure options. Explicitly neutralize ambient PGOPTIONS/PGSSLMODE/PGPORT/PGDATABASE/PGUSER/PGPASSWORD affecting the chosen config. No session startup read-only/timeout options copied to PgBouncer: enforce read transactions using BEGIN READ ONLY and transaction-local settings on the same checked-out client, as well as future actual least-privilege role grants. Config use does not prove those future role grants.
4. Small fixed pool (max2), explicit connection/idle/lifetime limits. Runtime query method implements existing TicketQueryable interface. Each operation must acquire/release its own client and use a read-only transaction with bounded per-statement and client deadlines. No growing background timers/healthchecks/keep-alives or unbounded waits; define one overall bounded deadline covering checkout and statements, and safely discard any late-acquired/in-flight client after a deadline. A Promise.race alone that leaks ownership is insufficient.
5. Prefer no automatic SQL replay. A failed operation returns a fixed sanitized connection error; destroy/discard a suspect client so a later explicit Retry can acquire a healthy connection. If any connect retry is introduced, it is at most once, before business SQL and inside the same deadline. Do not retry auth/TLS/permission/config/SQL errors. Document this distinction clearly.
6. Handle idle-pool errors without an unhandled exception or leaking error text; discard behavior of the real driver must be understood. close() idempotently prevents new queries and bounds cleanup. It must not close any independently owned shared DB or process. Log only fixed messages and constrained error codes; do not retain raw errors as public causes/details.
7. Meaningful offline tests must include: invalid config no factory use; ambient env cannot downgrade TLS or change target; actual pg config/TLS behavior where practicable with owned loopback TLS fixtures (no connection to Neon/native PostgreSQL); exact same-client transaction setup/read/release; business error/rollback cleanup and redaction; hung/late checkout or query deadline cleanup; idle errors; stale client followed by successful explicit Retry; close concurrency/idempotence and query after close. Existing local behavior/tests stay unchanged. Fakes are not a live Neon wake-up demonstration.
