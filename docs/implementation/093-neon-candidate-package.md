# Offline Neon backend candidate093

Prepared November7,2026 under contract090. This module prepares and verifies a **backend-only offline candidate**, distinctly marked `platypus-neon-backend-candidate` / `neon-postgres-ssm-v1`. It does not build the application, compose frontend graphs, acquire credentials, query PostgreSQL or SSM, invoke AWS, dispatch CodeBuild/Actions, or publish anything. Root owns full frontend composition and all ordinary delivery integration. The existing fixture publisher must continue refusing this distinct candidate.

## Interface and ownership

Owned implementation: `scripts/neon-aws/package.mjs` and `package.test.mjs`; this report. Infrastructure092 supplies `validateNeonRuntimeConfig`, `neonBackendTemplate` and `computeNeonBackendRevision`. The coordinator supplies the verified/pinned direct esbuild dependency and compiled `apps/server/dist/neon-lambda.js`; backend091 owns that handler.

`prepareNeonCandidate({root?,candidate,sourceSha,runtimeConfig})` returns `{directory,manifest,manifestSha256,codeSha256,backendRevision,totalBytes}`. `root` is a test seam/defaults to the repository root; the CLI cannot override it. Candidate names are bounded lowercase letters/digits/hyphens. Every output is under the selected marked workspace's `.local/neon-aws/candidates/<candidate>`. Output is never overwritten, repaired or deleted by this module; failed attempts retain their reserved names.

`verifyNeonCandidate({root?,candidate,expectedSourceSha,expectedRuntimeConfig,expectedManifestSha256})` requires **external** exact source, nonsecret configuration and candidate-manifest hash. Verification never trusts the candidate to choose its own expected account, endpoint, secret version or source. It returns the same safe receipt fields. The coordinator must bind the receipt/hash into its separate full frontend candidate. Source SHA is an explicit provenance input, not proof by itself that an arbitrary local compiled directory came from that commit: the coordinating clean build and exact-source CI provide that evidence.

Bounded explicit CLI operations are `prepare` and `verify`, accepting only `--candidate`, `--source-sha`, `--runtime` plus mandatory `--manifest-sha256` for verify. Runtime JSON must be a bounded ordinary file within the repository. There are no profile, endpoint, password, arbitrary environment, arbitrary output/root, publication or retry arguments. CLI failures print a fixed message without echoing arguments, ambient credentials or child stderr.

## Bundle and verification boundaries

esbuild0.28.2 bundles the compiled handler and dependencies into one Node24 ESM `lambda.js`, with `createRequire(import.meta.url)` for bundled CommonJS dependencies and a `type:module` package marker. No sourcemap is generated. The metafile must show only built-in Node external imports; `.node` or sourcemap inputs and external package imports are refused. `NODE_PG_FORCE_NATIVE` is fixed false for the bundle. The optional `pg-native` import is intercepted by a fixed throwing module, so it cannot load a native binary. Ordinary pure JavaScript PostgreSQL and SSM SDK classes remain available. No code is imported or invoked by preparation itself.

The existing `scripts/aws/archive.ps1` creates `backend.zip` and extracts its own just-created bytes into `lambda-extracted`. It runs hidden, with a bounded timeout/buffer and a small child environment containing only Windows/temp/path necessities and the three owned archive paths; no AWS/PG/Neon credential variables are forwarded. It writes only its candidate, never a global temp archive or shared build directory. The prepared/extracted graph is exactly `lambda.js` and `package.json`.

The canonical manifest binds source, kind/runtime variant, canonical nonsecret runtime JSON, generated backend template, ZIP hexadecimal/base64 hashes, infrastructure092 backend revision (including secret version), fixed bundler settings, exact inventory and byte total. Manifest selection is additionally pinned by its externally retained SHA256. All files, including redundant prepared/extracted copies and the manifest, fit a combined32MiB ceiling. Ordinary single-link files, no linked parents, safe case-unique filenames, exact directories and no extra/missing files are required. Configuration and template must still match their reviewed generators, even if a caller recomputes inventory hashes.

Verification re-parses the ZIP in memory using the existing strict artifact ZIP parser: bounded expansion, CRC, central/local records, duplicate/case collisions, traversal, links, devices, unsupported compression/ZIP64/extras and unlisted data are checked before comparing its exact two-file inventory and byte-for-byte equality against both prepared/extracted copies. No untrusted ZIP extraction is performed during verification.

The full candidate contains a copied backend candidate under `backend`, Shell and all three remote graphs under `objects`, canonical same-origin federation references, an active runtime pointer and exact rollback document/pointer copies. The nested backend verifier permits only an explicit bounded release name selecting `.local/neon-aws/releases/<release>/backend`, preserving its strict default candidate path and all external pins. This format is deliberately **not** an existing fixture delivery bundle.
